Bounding work with WithTimeout

Same as WithCancel, but the context also presses its own stop button after a duration. This is how you say "wait at most 20ms for this slow thing, then give up".

The idea

You still get a cancel function, and you still watch ctx.Done(). The only new thing: the context cancels itself when the timer runs out. The example makes the work (1 second) much slower than the timeout (20ms), so the timeout always wins — the result is deterministic.

New habit introduced here: defer cancel(). Even when the timeout will fire on its own, you still call cancel to release the resources Go set up to track the timer. It's never wrong to call it, and leaking it is a real bug. Make it reflexive.

The code that matters

ctx, cancel := context.WithTimeout(context.Background(), 20*time.Millisecond)
defer cancel() // Always, even though the timeout fires first.

result := make(chan string, 1) // Buffered so the slow worker never blocks.
go fetch(ctx, result)          // fetch takes a full second.

select {
case data := <-result:   // Would win only if work beat the timeout.
    fmt.Println("got:", data)
case <-ctx.Done():        // Fires after 20ms. ctx.Err() says why.
    fmt.Println("gave up:", ctx.Err())
}

Run it

18-context/04-with-timeout/main.go

Run

go run ./18-context/04-with-timeout

Expect

gave up: context deadline exceeded

Try: change the timeout to 2 * time.Second. Predict which select case wins and what prints.

Check yourself

Work needs 1s, the timeout is 20ms. Which select case wins?

The timer closes Done() after 20ms, long before the 1s result arrives, so the <-ctx.Done() case is ready first.

In short

WithTimeout = self-cancelling after a duration, plus defer cancel(). Next: the same, but at a fixed clock moment instead of a duration.
