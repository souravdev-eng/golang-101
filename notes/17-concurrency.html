Goroutines and channels

This folder starts work concurrently and then coordinates it: first by waiting for it, then by passing values over a channel. By the end you'll be able to read the two most common concurrency shapes in Go code.

What this folder is for

Concurrency is a big reason teams choose Go. You'll meet it in servers, workers and pipelines. This topic is an introduction to the vocabulary: go, sync.WaitGroup, chan, <- and close. It isn't a full course on concurrent design.

JS/TS you know

const work = (async () => {
  console.log("worker: packed lunch");
})();
await work;
console.log("main: ready to leave");

Go equivalent

var workers sync.WaitGroup
workers.Add(1)
go func() {
    defer workers.Done()
    fmt.Println("worker: packed lunch")
}()
workers.Wait()
fmt.Println("main: ready to leave")

The comparison only goes so far. JS runs your code on one thread with an event loop. Goroutines are lightweight threads that Go schedules for you, and they can run in parallel (Tour: Goroutines).

The vocabulary

go f()
Starts f in a new goroutine and carries on at once, without waiting for it.
sync.WaitGroup
A counter of unfinished work. Add(n) registers work, Done() marks one piece finished, and Wait() blocks until the count reaches zero (sync.WaitGroup).
make(chan string)
Creates a channel: a pipe that carries values of one type between goroutines (Tour: Channels).
ch <- v · v := <-ch
Send a value, receive a value. The arrow shows which way the data flows.
close(ch) · for v := range ch
The sender closes the channel when it's finished. range keeps receiving until the channel is closed and empty (Tour: Range and Close).

What to look for in each example

Run every command from the repository root, the folder that contains go.mod.

01 · Start and wait for a goroutine

17-concurrency/01-goroutine/main.go

  • Add(1) comes before the go line, so the work is registered before it can possibly finish.
  • defer workers.Done() uses Topic 14: it marks the work done however the function exits.
  • workers.Wait() is what guarantees the order of the two lines. The code has no sleep.

Run

go run ./17-concurrency/01-goroutine

Expect

worker: packed lunch
main: ready to leave

Try: change the worker's message. Check that it still prints before the main line.

02 · Send, receive, and close

17-concurrency/02-channels/main.go

  • sendLunches runs in its own goroutine and sends two values, then closes the channel.
  • The channel is unbuffered: each send waits until main is ready to receive. That hand-off keeps the two goroutines in step.
  • for lunch := range lunches ends by itself once the channel is closed. The sender closes it; the receiver never does.

Run

go run ./17-concurrency/02-channels

Expect

received: sandwich
received: fruit
all lunches received

Try: send "water" before close. Predict the extra output line.

Gotchas coming from JS/TS

  • Nothing is awaited automatically. When main returns, the program exits without waiting for other goroutines (Go spec: Program execution). Wait for them explicitly.
  • A goroutine isn't a Promise. go f() gives you no return value, so results travel back over a channel.
  • If you receive from a channel that nobody will ever send to, your code blocks forever. If every goroutine is stuck, Go stops with all goroutines are asleep - deadlock!.
  • Sending on a closed channel causes a panic. Only the sender should close (Tour: Range and Close).

Check yourself

In example 01, you delete workers.Wait(). What can happen?

Without Wait, main can print and return before the goroutine runs. The program then exits without it.

Who should close a channel?

Only the sender knows when there's nothing left to send. A receiver that closed the channel could make the sender panic on its next send.

In short

  1. go f() starts concurrent work. main won't wait unless you tell it to.
  2. Use sync.WaitGroup when you only need to wait for work to finish.
  3. Use a channel to pass values. The sender closes it, and range receives until it's closed.
