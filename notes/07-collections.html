Arrays and slices

You are collecting player scores. You need to add scores, inspect a few of them, and pass the list to a function. In Go, you will usually use []int, a slice. The important question is: when do two slices share the same scores, and when do they stop sharing?

Read sections 1–6 as one lesson (~10 min), then predict and run the examples. The expandable sections add optional detail. For revision, jump to Check yourself and Revision card.

1 · A slice describes data stored elsewhere

Think of a slice as a small value with three pieces of information, often called its header: a reference to its starting element, its length, and its capacity. You do not manage this header yourself; Go updates it through slicing and append.

An array is the fixed-size storage underneath. A slice literal such as scores := []int{10, 20} creates a slice and its backing array for you. You can use slices without declaring an array first.

Keep this model: copying a slice copies its description. It does not copy the elements. This explains sharing, growth, and function calls. Go blog: slice internals.

Arrays: the one-minute contrast

[3]int is an array type; []int is a slice type. An array's length is part of its type, so [3]int and [4]int differ. Assigning an array copies its elements; assigning a slice copies its header.

scores := [3]int{10, 20, 30}
other := scores
other[0] = 99
fmt.Println(scores, other) // [10 20 30] [99 20 30]

Arrays fit values with a size fixed by the problem, such as a 32-byte hash. Use slices for ordinary lists. Optional practice: go run ./07-collections/01-arrays.

2 · Length decides access; capacity decides growth

len(s) counts the elements currently in the slice. Valid element indexes are 0 through len(s)-1. cap(s) is the maximum length reachable by reslicing from this slice's start, without allocating another array. Spare append room is cap(s) - len(s).

scores := make([]int, 2, 4)
scores[0], scores[1] = 10, 20
fmt.Println(scores, len(scores), cap(scores)) // [10 20] 2 4

// scores[2] = 30 would panic: index 2 is outside len, despite cap 4.
scores = append(scores, 30)
fmt.Println(scores, len(scores), cap(scores)) // [10 20 30] 3 4

make([]T, length, capacity) creates storage and sets both numbers. Existing elements receive the type's zero value. Choose the length based on how you intend to fill the slice:

CreationWhat you getHow to fill it
[]int{10, 20}Known values; len 2, cap 2Use immediately
make([]int, 3)[0 0 0]; len 3, cap 3Assign s[i] = value
make([]int, 0, 3)Empty; len 0, cap 3Use s = append(s, value)
var s []intNil slice; len 0, cap 0Append as values arrive

Common mistake: make([]int, 3) followed by appending three scores produces six elements, starting with three zeros. Reserve with length 0 when you plan to append. Built-ins: make, len, and cap.

3 · Slicing creates another view of the same elements

s[low:high] includes low and excludes high. The resulting slice starts indexing at 0. For this two-index form, len = high - low and cap = cap(s) - low. The high bound changes length, but does not limit capacity.

scores := []int{10, 20, 30, 40}
middle := scores[1:3]
middle[0] = 99
fmt.Println(scores) // [10 99 30 40]
fmt.Println(middle, len(middle), cap(middle)) // [99 30] 2 3

alias := scores // This also shares the backing array.
alias = alias[:2]
fmt.Println(len(scores), len(alias)) // 4 2: lengths are separate.

The write changes shared data. Reslicing changes only the receiving variable's header. s[:2] means start at 0; s[2:] means stop at len(s); s[:] keeps the same range and still shares.

JS/TS bridge: JavaScript's array.slice(1, 3) makes a shallow copy. Go's s[1:3] shares storage. And b := s gives b its own length and capacity, even though the elements are shared.

Why can reslicing reach beyond length?

Indexing is limited by length; a slice's explicit upper slicing bound may reach its capacity. After s := make([]int, 2, 4), s[2] panics, but expanded := s[:4] is valid. The expanded view exposes the reserved slots. They may already contain values written through another slice.

For simple slicing of a slice, bounds must satisfy 0 ≤ low ≤ high ≤ cap(s). Omitted high still means len(s). Invalid bounds at run time panic. Specification: slice expressions.

4 · Append may keep or replace the backing array

A · Room remains: the elements stay shared

scores := make([]int, 2, 4)
scores[0], scores[1] = 10, 20
alias := scores
scores = append(scores, 30)
scores[0] = 99
fmt.Println(scores) // [99 20 30]
fmt.Println(alias)  // [99 20]: shared elements, old length 2

B · No room remains: the result uses new storage

scores := []int{10, 20} // len 2, cap 2: deliberately full
alias := scores
scores = append(scores, 30) // Needs a new array.
scores[0] = 99
fmt.Println(scores) // [99 20 30]
fmt.Println(alias)  // [10 20]: still on the old array

append returns the updated slice; it does not update every variable sharing the old storage. Usually write s = append(s, x). You can also assign to another variable or return the result. To append a slice, use s = append(s, more...). Go chooses the new capacity; do not rely on an exact growth factor. Built-in append.

Watch sub-slices: spare capacity may include elements visible through another slice. Appending can overwrite those elements. The example below shows why, and how limiting capacity changes the result.

Important edge case: appending a sub-slice can overwrite its neighbour 
scores := []int{10, 20, 30, 40}
firstTwo := scores[:2] // len 2, cap 4
firstTwo = append(firstTwo, 99)
fmt.Println(scores) // [10 20 99 40]

Append starts writing at the sub-slice's length. Because there is spare capacity, it writes into scores' existing slot 2.

Use a full slice expression to limit append room:

scores := []int{10, 20, 30, 40}
firstTwo := scores[:2:2] // len 2, cap 2
firstTwo = append(firstTwo, 99) // Forces new storage.
firstTwo[0] = 77
fmt.Println(scores)   // [10 20 30 40]
fmt.Println(firstTwo) // [77 20 99]

s[low:high:max] gives capacity max - low. Limiting capacity does not copy elements: before this append, firstTwo[0] = 77 would still change scores. For an independent copy immediately, use section 6. Specification: full slice expressions.

5 · Functions get a copy of the slice header

This is the same rule as alias := scores. Go passes arguments by value: the function gets its own header, pointing at the same elements. Writing s[0] affects the caller. Assigning an appended or resliced header to the local s does not change the caller's length.

package main

import "fmt"

func addScore(s []int) []int {
    s[0] = 99          // Write to shared storage.
    s = append(s, 30)  // Update the local header.
    return s          // Give that header back to the caller.
}

func main() {
    scores := make([]int, 2, 3)
    scores[0], scores[1] = 10, 20
    updated := addScore(scores)
    fmt.Println(scores)  // [99 20]: caller's length is still 2
    fmt.Println(updated) // [99 20 30]
    scores = updated     // Caller keeps the new header.
}

For a function that changes length, use the pattern scores = addScore(scores). A slice parameter can mutate existing elements without *[]int. The returned slice handles the length change whether append reuses storage or allocates. Effective Go: slices and functions.

6 · Copy elements when you need independent storage

If you want to edit a snapshot without changing the original, allocate a destination, then copy the elements:

scores := []int{10, 20, 30}
snapshot := make([]int, len(scores))
n := copy(snapshot, scores)
snapshot[0] = 99
fmt.Println(n, scores, snapshot) // 3 [10 20 30] [99 20 30]

copy(dst, src) returns the count copied, which is min(len(dst), len(src)). It does not allocate or grow dst. An empty destination, even one with reserved capacity, copies zero elements. Built-in copy.

The standard library also offers snapshot := slices.Clone(scores) after import "slices" (available in this course's Go 1.22). Both approaches make a shallow copy: a new outer slice, with elements copied as values. If an element itself holds a pointer, map, or another slice, that referenced data can still be shared. slices.Clone documentation.

Memory consequence: a small view can retain a large array

If you keep just large[:10], the view still refers to the original storage, so a large backing array can remain in memory. Copy the small portion if it must outlive the large data. Restricting its capacity does not detach the array. Go blog: retaining backing arrays.

Everyday slice habits

Range gives you an element value; use the index to replace it 
scores := []int{10, 20}
for _, score := range scores {
    score += 5 // Changes the local int, not the slice element.
}
fmt.Println(scores) // [10 20]
for i := range scores {
    scores[i] += 5
}
fmt.Println(scores) // [15 25]

Use for _, score := range scores to read values. Use for i := range scores when replacing elements. This connects to Topic 05 · Loops.

Nil and empty slices both work as empty lists 
var scores []int
empty := []int{}
fmt.Println(len(scores), cap(scores), scores == nil) // 0 0 true
fmt.Println(len(empty), cap(empty), empty == nil)    // 0 0 false
scores = append(scores, 10) // Appending to nil works.
fmt.Println(scores) // [10]

Both have zero elements, can be ranged over, and can be appended to. Use len(s) == 0 to check whether a list has no elements. Use s == nil only when you care about that distinction. Slices cannot be compared to each other with ==; use slices.Equal(a, b) for comparable element types. slices.Equal.

Check yourself

Answer from the header-and-array model, without running the code.

s := make([]int, 0, 3). Can you write s[0] = 10?

Indexing uses length. There are no elements yet. s = append(s, 10) makes the length 1.

s := []int{10, 20, 30, 40}, then part := s[1:3]. What are part's length and capacity?

Length is 3 − 1. Capacity is 4 − 1, measured from part's starting position.

s := []int{10, 20, 30}, part := s[:2], then part = append(part, 99). What does s contain?

Part has length 2 and capacity 3. Append reuses the array and overwrites slot 2. S keeps its length 3.

s := []int{10, 20}, b := s, s = append(s, 30), then s[0] = 99. What does b contain?

The literal has capacity 2. Appending a third element creates a new array for s; b stays on the old array.

A function receives s []int, writes s[0] = 99, and assigns s = append(s, 30) locally. The caller ignores the new header. What can the caller observe?

The element write uses shared storage. The append updates the function's local header. Return that header and assign it in the caller to retain the longer slice.

Explain aloud: how would you make a safe snapshot?

Allocate with make([]T, len(src)) and copy, or use slices.Clone(src). The outer storage is independent; copying is shallow.

Revision card

  1. Header + backing array: assigning or passing a slice copies the header and shares the elements.
  2. Length = access; capacity = reslice limit. Spare append room is cap - len.
  3. Slicing shares. The result has its own start, length, and capacity.
  4. Append returns a header. Enough capacity means reuse; exceeding capacity means new storage.
  5. Copy for independence. Allocate and copy, or use slices.Clone.

For any slice puzzle: draw each header → identify shared storage → compare new length with capacity → track element writes separately from header assignments.
