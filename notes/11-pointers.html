Pointers and changes

This folder answers one question: when I pass something to a function, can that function change my copy? In Go the answer is no, unless you pass a pointer.

What this folder is for

Go always passes arguments by value. The function gets a copy, just as an assignment would make one (Go FAQ: pass by value). A pointer is a value that holds the address of another value. When you pass the pointer, the function can reach the original.

JS/TS you know

// Objects are shared, so this changes the caller's object
function bump(c: { value: number }) {
  c.value++;
}
// Numbers are copied, so this does not
function bumpNum(n: number) {
  n++;
}

Go equivalent

// A struct is copied unless you pass a pointer
func bump(c *Counter) {
    c.Value++
}
func bumpCopy(c Counter) {
    c.Value++ // changes the copy only
}

In JS the type decides whether something is shared. In Go you decide, by passing a value or a pointer to it.

The three symbols

*int
In a type, * means "pointer to". *int is a pointer to an int (Tour: Pointers).
&count
& takes the address of a variable and gives you a pointer to it.
*count = …
On a pointer value, * reads or writes the thing it points to. This is called dereferencing.
nil
A pointer that points nowhere. It's the zero value of every pointer type. Dereferencing nil causes a runtime panic, which crashes the program.
func (c *Counter) Increment()
A pointer receiver. The method can change the struct it was called on (Tour: Pointer receivers).

How to choose

A simple rule while you're learning: if a method needs to change the struct, use a pointer receiver. The Tour adds a second reason: pointer receivers avoid copying large structs. It also says to keep all of one type's methods on the same kind of receiver (Tour: Choosing a value or pointer receiver).

Gotchas coming from JS/TS

  • A struct passed to a function is a copy, even though in JS an object would be shared. If you change the copy, the caller never sees it.
  • * means two things. In a type (*int) it means "pointer to". In an expression (*p) it means "the value at". Read the context.
  • There's no pointer arithmetic like in C. You can't do p + 1 (Tour: Pointers).
  • A nil pointer dereference is a crash, not undefined. It's the Go version of "cannot read properties of undefined".

Check yourself

x := 5, then you call addToCopy(x), which does count++. What is x afterwards?

The function got a copy of x. Only the copy went up. To change x, pass &x to a function that takes *int.

A method has to change a field of its struct. Which receiver should it use?

A pointer receiver such as (c *Counter) works on the original. A value receiver changes a copy, which is thrown away when the method returns.

In short

  1. Go passes everything by value. A function gets a copy.
  2. &x gives you a pointer. *p reads or writes through it. The zero pointer is nil.
  3. Use a pointer receiver when a method has to change its struct.
