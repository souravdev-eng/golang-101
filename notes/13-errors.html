Errors

This folder shows the most common pattern in all Go code: a function returns its result and an error, and the caller checks the error straight away. There's no try/catch.

What this folder is for

In Go, an expected failure is just a value that the function returns. You'll see if err != nil in nearly every Go file you open, so learning to read it quickly is a big win (Go blog: Error handling and Go).

JS/TS you know

try {
  const each = share(8, 0);
  console.log(each);
} catch (e) {
  console.log("cannot share:", e.message);
}

Go equivalent

each, err := share(8, 0)
if err != nil {
    fmt.Println("cannot share:", err)
    return
}
fmt.Println(each)

The error is part of the function's signature, (int, error), so you can see which calls can fail without reading their code.

Key ideas

(int, error)
The function returns two values. By convention the error comes last.
error
A built-in interface with one method, Error() string. Any type with that method is an error (Tour: Errors). That's Topic 12 at work.
nil
"No error". If err == nil, the call worked.
errors.New("…")
Creates a simple error with a message (errors.New).
if err != nil { … return }
Check right after the call. Handle the error, then stop before you use a result that isn't valid.
_
The blank identifier. It throws away a return value you don't need, as in _, err = share(8, 0).

What to look for in each example

Run every command from the repository root.

01 · Returning and checking errors

13-errors/01-return-check/main.go

  • In share, find the two return lines. The failure path returns 0, errors.New(…). The success path returns apples / people, nil.
  • In main, look at the shape each, err := share(8, 2) followed straight away by if err != nil.
  • The return inside that if leaves main early, so the code never uses a bad result.
  • The second call uses _ for the result and = instead of :=, because err already exists.

Run

go run ./13-errors/01-return-check

Expect

each: 4
cannot share: people must be positive

Try: pass a negative number of people in the second call. Predict the output first.

02 · Handling a library error

13-errors/02-parse/main.go

  • strconv.Atoi turns text into an int. It's like parseInt, but it returns (int, error) (strconv.Atoi).
  • The standard library uses exactly the same value-plus-error pattern as your own code.
  • Where parseInt("many") gives you NaN, Go gives you a real error you have to deal with.

Run

go run ./13-errors/02-parse

Expect

quantity: 12
invalid quantity: "many"

Try: pass "3.5". Atoi expects a whole number, so predict which branch runs.

What about panic?

Go does have panic, which stops the program much like an uncaught exception. It's meant for bugs and truly impossible situations, such as dereferencing a nil pointer (Topic 11). For failures you expect, like bad input or a missing file, return an error (Effective Go: Errors).

Gotchas coming from JS/TS

  • Nothing forces you to check err, but ignoring it is a bug. Read every if err != nil as "this is what happens when it fails".
  • When err != nil, the other return value is usually meaningless, like the 0 here. Don't use it.
  • Error messages are lowercase with no final full stop, for example "people must be positive". That's because they often get joined into longer messages (Go wiki: Error strings).

Check yourself

A call returns result, err. What does err == nil tell you?

nil means "no error", so the call worked and result is safe to use.

Where does the error usually go in a Go function's results?

By convention the error is the last result, as in (int, error). Go doesn't throw expected errors. It returns them.

In short

  1. A function that can fail returns (value, error). The error comes last.
  2. Check if err != nil straight after the call, handle it, and return early.
  3. error is just an interface with Error() string. nil means success.
