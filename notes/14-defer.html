Defer

This folder shows how to schedule a call to run later, when the current function returns. By the end you'll be able to predict the order in which cleanup lines run.

What this folder is for

Real Go code often opens something (a file, a lock, a connection) and must close it again. defer lets you write the cleanup right next to the setup, and Go runs it at the end of the function for you. You'll see defer all over real projects, so it pays to read it fluently.

JS/TS you know

function pack() {
  console.log("start packing");
  try {
    console.log("packing done");
  } finally {
    console.log("close box");
  }
}

Go equivalent

func pack() {
    fmt.Println("start packing")
    defer fmt.Println("close box")
    fmt.Println("packing done")
}

Both print close box last. A deferred call runs just before the function that contains it returns (Go spec: Defer statements).

The three rules

Runs at function return
The call waits until the surrounding function finishes. Not the end of a block or loop: the end of the function.
Last in, first out
Several defers stack up. The last one written runs first (Tour: Stacking defers).
Arguments are read now
The values passed to the deferred call are worked out at the defer line. Later changes to a variable don't affect them (Tour: Defer).

Where you'll see it in real code

The usual pattern is "open, check the error, then defer the close" (Go blog: Defer, Panic, and Recover):

f, err := os.Open("list.txt")
if err != nil {
    return err
}
defer f.Close() // runs however this function returns

Errors are Topic 13. The point here is only the shape: the cleanup sits one line below the setup.

Gotchas coming from JS/TS

  • defer is tied to the function, not the { } block. A defer inside a loop doesn't run each time round. They all pile up until the function returns.
  • The arguments are captured straight away. If you want the value at the end, the deferred call has to read the variable later, for example inside an anonymous function.
  • There's no try/finally in Go. defer is the tool that does that job.

Check yourself

Three defers are written in the order A, B, C. In what order do they run?

Deferred calls are stacked: last in, first out. C was written last, so it runs first.

label := "tea", then defer fmt.Println(label), then label = "coffee". What does the deferred call print?

The argument label is evaluated at the defer line, while it still holds "tea". The call itself runs later.

In short

  1. defer schedules a call for when the surrounding function returns.
  2. Several defers run in reverse order.
  3. Arguments are evaluated at the defer line, not when the call runs.
