Interfaces

This folder shows how different types can be used in the same place because they share the same method. It feels close to TypeScript's structural typing, but it's checked when you compile and it's based only on methods.

What this folder is for

An interface lists method signatures. Any type that has those methods can be used as that interface. You never write implements (Tour: Interfaces are implemented implicitly).

JS/TS you know

interface Greeter {
  greeting(): string;
}
// Any object with greeting() fits
function welcome(g: Greeter) {
  console.log(g.greeting());
}

Go equivalent

type Greeter interface {
    Greeting() string
}
// Any type with Greeting() fits
func welcome(g Greeter) {
    fmt.Println(g.Greeting())
}

They look almost the same. The big difference is that a Go interface describes behaviour only, meaning methods. It can't require fields, but TS interfaces can.

Key ideas

type Greeter interface { … }
A set of method signatures. A value of type Greeter can hold any value whose type has all of those methods (Tour: Interfaces).
Implicit satisfaction
Person and Robot never mention Greeter. They each have a Greeting() string method, and that's enough.
Concrete type
The real type inside an interface value, such as Person or Robot. welcome doesn't know or care which one it got.
error
You'll use a built-in interface in the very next topic: error is an interface with one method, Error() string (Tour: Errors).

Why Go works this way

Because a type doesn't have to declare that it satisfies an interface, you can write a small interface for just the behaviour your function needs, and existing types will fit it automatically. Go's standard library leans on this heavily with one-method interfaces such as io.Reader and fmt.Stringer (Effective Go: Interfaces).

Gotchas coming from JS/TS

  • An interface can list methods only, never fields. interface { Name string } is not valid Go.
  • The method has to match exactly: same name, same parameter types, same result types. Greeting() string and greeting() string are different methods.
  • It's still checked when you compile. If you pass a type that's missing a method, the build fails with a message that names the missing method.
  • If a method has a pointer receiver, only the pointer type satisfies the interface. So you'd pass &thing, not thing (Tour: Interfaces).

Check yourself

How does Robot come to satisfy Greeter?

Satisfaction is implicit. If a type has every method the interface lists, with matching signatures, it satisfies the interface. No keyword is needed.

What can a Go interface require from a type?

A Go interface describes behaviour, so it lists methods only. That's different from TS, where an interface can require properties too.

In short

  1. An interface is a list of methods. Any type with those methods satisfies it.
  2. There's no implements keyword, but the compiler still checks the match.
  3. Functions that accept an interface work with any type that fits, now or in the future.
